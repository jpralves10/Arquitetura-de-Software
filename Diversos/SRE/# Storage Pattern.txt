*** polyglot persistence pattern ***

O Polyglot Persistence Pattern (Persistência Poliglota) é uma abordagem arquitetural no desenvolvimento de software que utiliza múltiplos tipos de tecnologias de banco de dados para atender a diferentes necessidades de armazenamento de dados dentro de uma única aplicação. 

Em vez de forçar todos os dados a caberem em um único banco de dados relacional (abordagem "one-size-fits-all"), essa estratégia "usa a ferramenta certa para o trabalho certo". O termo, popularizado por Martin Fowler e Pramod Sadalage, faz um paralelo com a "programação poliglota", onde diferentes linguagens são usadas no mesmo projeto. 

Por que usar a Persistência Poliglota?
1. Variedade de Dados: Aplicações modernas lidam com dados estruturados, semiestruturados (JSON) e não estruturados (logs, imagens, grafos).
2. Otimização de Performance: Bancos NoSQL podem oferecer escalabilidade horizontal superior para alto volume de escrita, enquanto bancos relacionais (RDBMS) são melhores para transações complexas (ACID).
3. Necessidades Específicas: Um sistema de recomendação funciona melhor com um banco de grafos (ex: Neo4j), enquanto sessões de usuário exigem velocidade (ex: Redis). 

Exemplo Prático de uma Aplicação E-commerce 
Em um sistema de e-commerce, a persistência poliglota pode ser aplicada assim:
- PostgreSQL/MySQL (Relacional): Usado para dados estruturados, transações financeiras e pedidos, garantindo consistência.
- MongoDB (Documento): Usado para o catálogo de produtos, permitindo flexibilidade na estrutura de atributos de diferentes categorias.
- Redis (Key-Value): Usado para cache de sessão e carrinho de compras, oferecendo velocidade extrema.
- Neo4j (Grafo): Usado para recomendar produtos "quem comprou isso, também comprou...".

Vantagens e Desvantagens

Vantagens
Performance: Alta performance por usar o DB ideal.
Escalabilidade: Escala melhor ao distribuir cargas.
Flexibilidade: Acomoda novos tipos de dados facilmente.

Desvantagens (Trade-offs)
Complexidade: Mais sistemas para gerenciar e monitorar.
Curva de Aprendizado: Equipe precisa conhecer múltiplas tecnologias.
Consistência: Difícil manter a consistência entre bancos diferentes.

Quando considerar esse padrão?
A persistência poliglota não é necessária para todos os projetos. Ela é indicada para: 
- Sistemas de Grande Escala: Onde um único banco de dados vira um gargalo (Netflix, Amazon).
- Projetos Estratégicos/Complexos: Projetos com requisitos de dados intensivos ou heterogêneos. 

Para a maioria dos projetos simples ou utilitários, a "ortodoxia relacional" (usar apenas RDBMS) ainda é preferível para evitar complexidade desnecessária.

***  database-per-service pattern ***

O padrão Database-per-Service (Banco de Dados por Serviço) é um princípio de design fundamental na arquitetura de microsserviços. Ele dita que cada microsserviço deve possuir e gerenciar seu próprio banco de dados privado e exclusivo. 

Isso significa que um serviço A não tem acesso direto ao banco de dados do serviço B. A interação com os dados de outro serviço só é permitida através de APIs (como REST) ou troca de mensagens/eventos. 

Principais Características
- Isolamento: Os dados de um serviço são privados e ocultos para os outros serviços.
- Propriedade: O serviço é o único responsável pela lógica de negócios e pela integridade dos seus próprios dados.
- Independência de Tecnologia: Como os bancos são separados, cada serviço pode usar o tipo de banco de dados mais adequado para sua necessidade (SQL, NoSQL, etc.). 

Por que utilizar (Vantagens)
1. Baixo Acoplamento: As alterações no esquema de banco de dados de um serviço não quebram outros serviços.
2. Escalabilidade Independente: Se o serviço de "Pedidos" está com alto tráfego, o banco de dados dele pode ser escalado separadamente do banco de dados do serviço de "Clientes".
3. Resiliência: Se o banco de dados de um serviço cair, os outros serviços continuam funcionando, limitando o impacto.
4. Otimização: Você pode escolher um banco orientado a documentos (NoSQL) para um serviço de catálogo e um banco relacional (SQL) para um serviço financeiro. 

Desafios (Desvantagens)
1. Complexidade em Consultas (Joins): Buscar dados que estão em dois serviços diferentes (ex: Pedido + Cliente) exige consultas via API, o que é mais complexo e lento que um SQL JOIN.
2. Consistência Distribuída: Manter a consistência de dados entre múltiplos bancos exige padrões complexos, como Saga Pattern, para transações distribuídas.
3. Gerenciamento Operacional: Gerenciar vários bancos de dados pequenos pode ser mais trabalhoso do que um grande banco compartilhado. 

Exemplo Prático
Em um e-commerce:
- Serviço de Pedidos: Usa PostgreSQL (relacional para transações financeiras).
- Serviço de Catálogo: Usa MongoDB (NoSQL para flexibilidade de produtos).
- Serviço de Recomendação: Usa Neo4j (banco de grafos). 

Se o "Serviço de Pedidos" precisa de dados do cliente, ele chama a API do "Serviço de Clientes" em vez de acessar a tabela de clientes diretamente.

*** sharad-database-per-service ***

O padrão Shared Database (Banco de Dados Compartilhado), frequentemente referenciado como Shared Database per Service ou Shared Data Pattern, é uma abordagem na arquitetura de software onde vários microsserviços ou aplicações utilizam o mesmo banco de dados físico ou instância para persistir seus dados. 

Diferente do padrão "Database per Service" (onde cada serviço tem seu próprio DB), este padrão centraliza o armazenamento.

Principais Características
- Centralização: Diferentes microsserviços acessam o mesmo banco de dados (ex: uma única instância PostgreSQL ou MySQL).
- Isolamento via Esquema (Schema): Em muitos casos, para evitar conflitos, cada serviço usa um schema diferente dentro do mesmo banco de dados, ou tabelas dedicadas.
- Acesso Direto: Serviços podem, tecnicamente, realizar queries diretamente nas tabelas de outros serviços (embora isso seja desencorajado). 

Vantagens
- Simplicidade: Mais fácil de gerenciar, configurar, fazer backup e monitorar, já que há menos instâncias de banco de dados.
- Consistência de Dados: Facilita a manutenção da consistência, permitindo transações (como joins ou rollbacks) entre tabelas de diferentes serviços.
- Latência Reduzida: Menor necessidade de chamadas de rede entre serviços para obter dados.
- Ideal para Legado: Útil na migração de um monolito para microsserviços, permitindo que a nova arquitetura consuma os dados da base existente. 

Desvantagens e Desafios
- Acoplamento Forte: Se um serviço alterar uma tabela compartilhada, outros serviços podem quebrar.
- Escalabilidade Limitada: O banco de dados torna-se um gargalo. Se um serviço tiver alta demanda, ele pode consumir todos os recursos (CPU/Memória), afetando todos os outros serviços.
- Complexidade de Manutenção: Requer coordenação rigorosa entre as equipes de desenvolvimento para evitar conflitos de schema.
- Segurança: Acesso direto à base de dados pode violar o isolamento de dados. 

Quando usar?
O Shared Database Pattern é recomendado quando:
1. A equipe é pequena: Gerenciar múltiplos bancos de dados é muito complexo.
2. Transações complexas: A aplicação exige transações ACID fortes entre tabelas de domínios diferentes.
3. Migração de Monolito: O sistema está sendo movido de uma aplicação monolítica para microsserviços de forma incremental. 

Nota: Em sistemas de microsserviços modernos, prefere-se geralmente o padrão "Database per Service" para garantir autonomia, mas o Shared Database é uma alternativa válida se a simplicidade for prioritária sobre o isolamento.

*** (CDC) change-data-capture ***

O Change Data Capture (CDC), ou Captura de Dados de Alteração, é um padrão de design de software e uma técnica de integração de dados utilizada para identificar, rastrear e registrar automaticamente as alterações (inserções, atualizações e exclusões) feitas em um banco de dados de origem. 

Em vez de copiar tabelas inteiras repetidamente para sincronizar sistemas (processamento em lote/batch), o CDC captura apenas os registros modificados e os aplica em sistemas de destino (como Data Warehouses, Caches ou sistemas de busca) quase em tempo real. 

Como funciona o CDC?
Existem três abordagens principais para implementar o CDC:

1. CDC Baseado em Log (Log-based): A forma mais eficiente e comum. A ferramenta CDC lê diretamente os logs de transação nativos do banco de dados (ex: WAL no PostgreSQL, Binary Log no MySQL, Redo Log no Oracle).
-- Vantagem: Não intrusivo, quase sem impacto no desempenho do banco de dados de produção.

2. CDC Baseado em Gatilho (Trigger-based): Gatilhos (triggers) são criados nas tabelas de origem para registrar qualquer alteração em uma tabela de histórico (tabela sombra).
-- Desvantagem: Pode causar sobrecarga no banco de dados, tornando as operações mais lentas.

3. CDC Baseado em Consulta (Polling/Timestamp): Consulta periodicamente tabelas à procura de novas linhas baseadas em um campo de data/hora ou versão.
-- Desvantagem: Menos eficiente, consome recursos de consulta e geralmente não detecta exclusões (deletes). 

Benefícios do CDC
- Tempo Real/Baixa Latência: Sincroniza dados instantaneamente, eliminando a espera por processamentos noturnos (ETL).
- Eficiência e Desempenho: Move apenas os dados alterados, reduzindo drasticamente o tráfego de rede e a carga sobre os sistemas de origem.
- Integridade dos Dados: Garante que o destino esteja perfeitamente alinhado com a origem, inclusive deletando registros que foram apagados na origem.
- Suporte a Streaming: Ideal para arquiteturas orientadas a eventos (Kafka) e análises em tempo real. 

Casos de Uso Comuns
- Replicação de Bancos de Dados: Sincronizar um banco de dados SQL primário com uma réplica para leitura ou alta disponibilidade.
- Data Warehouse / Data Lakehouse: Atualizar BigQuery, Snowflake ou Databricks continuamente com dados operacionais.
- Migração de Dados com Zero Downtime: Migrar bancos de dados para a nuvem sem precisar interromper o sistema de produção.
- Microsserviços: Propagar alterações de dados de um serviço para outros serviços sem acoplamento direto. 

Ferramentas Populares
- Debezium: Plataforma de código aberto (open-source) muito popular que se integra ao Kafka.
- Striim: Plataforma comercial de nível empresarial para streaming e CDC.
- Oracle GoldenGate: Ferramenta robusta e proprietária da Oracle.
- Datastream (Google Cloud): Serviço gerenciado para replicação de bancos de dados para BigQuery.
- AWS Database Migration Service (DMS): Serviço da Amazon para migração e replicação. 

Em resumo, o CDC é fundamental para empresas que buscam modernizar sua infraestrutura de dados e tomar decisões baseadas em informações atuais, não em relatórios "de ontem

- Uma mudança de um sistema é capturado e adiciona/atualiza um outro target
- Baixa Latência de propagação, "near real time"
- Remove a complexidade de você garantir consistência somente via código
- Simplifica o processo de replicação e existem soluções/softwares
- Muito usado para Warehouse
- Desacoplamento de task de replicação da sua aplicação
- Uma nova tecnologia em sua stack de ferramentas
- Compatibilidade limitada (nem todos os CDCs falam com a base de origem ou destino)
- Eventual Consistency

*** Transactional Outbox Pattern ***

O Transactional Outbox Pattern (Padrão de Caixa de Saída Transacional) é um padrão de projeto de software utilizado em arquiteturas de microsserviços para garantir a consistência de dados e a entrega confiável de mensagens (eventos) entre serviços. 

Ele resolve o problema de "dupla escrita", onde um serviço precisa atualizar seu próprio banco de dados e, ao mesmo tempo, notificar outros serviços via message broker (como RabbitMQ ou Kafka), mas falha em um deles. 

O Problema: Inconsistência de Dados
Imagine que um microserviço de "Pedido" salva um pedido novo no banco, mas o Message Broker cai antes de receber a notificação.
- Resultado: O pedido existe no banco, mas outros serviços (estoque, pagamento) nunca saberão dele. O sistema fica inconsistente. 

A Solução: Transactional Outbox Pattern
Em vez de enviar a mensagem diretamente para o broker, o serviço:
1. Salva a entidade de negócio (ex: Pedido).
2. Salva a mensagem do evento em uma tabela especial no mesmo banco de dados, chamada Outbox, dentro da mesma transação. 

Como ambas as ações ocorrem na mesma transação, ou ambas são confirmadas (commit) ou ambas são desfeitas (rollback), garantindo atomicidade. 

Como Funciona (Fluxo)
1. Operação de Negócio: A aplicação inicia uma transação no banco.
2. Escrita Dupla Local: A aplicação insere o pedido na tabela Pedidos e o evento na tabela Outbox.
3. Commit: A transação é finalizada. Se falhar, nada é salvo.
4. Message Relay/Publisher: Um processo separado (em segundo plano) monitora a tabela Outbox, lê novas mensagens, publica no Message Broker e marca as mensagens como enviadas (ou as deleta). 

Componentes Principais
- Tabela Outbox: Tabela no banco de dados relacional (ou noSQL) que funciona como uma fila temporária de eventos.
- Message Publisher/Relay: Um serviço ou worker que lê a tabela Outbox e envia para o broker (pode ser via polling ou lendo o log de transações do banco/CDC). 

Vantagens
- Consistência Eventual: Garante que o evento será publicado se a transação do banco for bem-sucedida.
- Resiliência: Se o Message Broker estiver fora do ar, as mensagens ficam seguras na Outbox e serão enviadas quando ele retornar.
- Sem Transações Distribuídas: Evita a complexidade de transações distribuídas (2PC) entre banco e broker. 

Desafios
Idempotência: Como o processo de envio pode tentar re-enviar mensagens em caso de falha na marcação de "enviado", o consumidor da mensagem deve ser capaz de lidar com a mesma mensagem múltiplas vezes. 

Resumo Visual
App -> [Transação: Salva Dado + Salva Evento na Tabela Outbox] -> Processo de Fundo -> Message Broker

- Como "atomicamente" garantir consistência entre dois destinos.
- Muito usado para garantir a atomicidade entre targets, nunca faz commit só em um target
- Resolve problema de dual-write com ACID
- Fácil de implementar e benéfico significativo
- Tira complexidade do lado da aplicação de garantir consistência através de
- Evita a necessidade de mudar arquitetura toda para event soucing
- "Latência" muito baixa de um insert
- Double de Write e possivelmente dobro de tamanho na base de dado
- Apps downstreams precisam garantir, se necessário, a tratativa de duplicidade
- Mensagerias geralmente pode ter MSG duplicadas e fora de ordem (ou FIFO)

*** desnormalização + desacoplamento ***

A combinação de desnormalização e desacoplamento é uma estratégia arquitetural poderosa, frequentemente utilizada para maximizar o desempenho de leitura e a escalabilidade de sistemas, especialmente no contexto de microserviços e alta demanda. 

Aqui está uma análise detalhada dos conceitos e como eles interagem:

1. Desnormalização (Otimização de Leitura)
- O que é: Processo de introduzir redundância intencional em um banco de dados relacional.
- Objetivo: Aumentar o desempenho de consultas (leitura), reduzindo ou eliminando a necessidade de joins complexos entre várias tabelas.
- Como funciona:
-- Duplicação de colunas frequentemente acessadas em uma única tabela.
-- Armazenamento de dados pré-calculados (ex: total de vendas).
-- Mesclagem de tabelas relacionadas.
- Custo: Aumenta o risco de inconsistência de dados (anomalias de atualização) e exige cuidado na manutenção da integridade. 

2. Desacoplamento (Independência de Serviços)
- O que é: Mover a dependência e o acoplamento de níveis baixos (como o banco de dados) para camadas mais elevadas, como APIs HTTP ou mensageria.
- Objetivo: Permitir que microsserviços evoluam, escalem e operem de forma independente.
- Vantagens: Aumenta a resiliência e tolera falhas (se um serviço cair, o outro continua operando), além de facilitar a fragmentação de dados. 

3. A Sinergia: Desnormalização + Desacoplamento
Quando aplicados juntos, a desnormalização e o desacoplamento permitem criar arquiteturas de leitura intensiva de alta performance:
- Modelo de Leitura vs. Escrita (CQRS): É comum usar um banco totalmente normalizado para o lado da escrita (garantindo consistência) e um modelo desnormalizado para o lado da leitura (otimizando a velocidade).
- Evolução e Escala: Ao desacoplar o banco de dados, é possível desnormalizar dados específicos para um microsserviço sem impactar o sistema principal.
- Técnicas de Desacoplamento:
-- Utilizar APIs para buscar dados agregados em vez de tabelas normalizadas.
-- Armazenar dados em formatos flexíveis (como JSONB) para facilitar a desnormalização.
- Cenários de Uso: Sistemas de relatórios, dashboards, e-commerce, e cenários de leitura intensa. 

Em resumo, a desnormalização melhora a performance de leitura, enquanto o desacoplamento resolve os problemas de dependência e escalabilidade, permitindo que a desnormalização seja feita de forma segura e eficiente.

*** database sharding ***

O Database Sharding (fragmentação de banco de dados) é uma técnica de escalabilidade horizontal que divide um banco de dados grande em partes menores e mais gerenciáveis, chamadas shards, distribuindo-as por vários servidores. Essa abordagem permite distribuir a carga de trabalho, melhorar a performance de consultas e aumentar a capacidade de armazenamento ao adicionar mais máquinas (nós). 

Principais Conceitos:
- Particionamento Horizontal: O sharding é, essencialmente, dividir linhas de tabelas grandes entre diferentes bancos de dados.
- Shards (Fragmentos): Cada fragmento reside em um servidor separado com seu próprio disco, memória e processador, operando de forma independente.
- Escalabilidade Horizontal (Scale-out): Permite o crescimento do sistema adicionando mais máquinas, em vez de depender de uma única máquina mais potente (escalabilidade vertical).
- Arquitetura Shared-Nothing: Os shards não compartilham dados ou recursos, o que aumenta a resiliência; se um shard falhar, os outros permanecem operacionais. 

Estratégias de Sharding (Como dividir os dados):
- Sharding por Chave (Range Based): Divide os dados com base em faixas de valores de uma coluna (ex: IDs de 1 a 1000 no Shard A, 1001 a 2000 no Shard B).
- Sharding por Hash: Aplica uma função hash a uma chave para determinar o shard, garantindo uma distribuição mais uniforme dos dados.
- Sharding por Diretório (Lookup): Utiliza um serviço de busca para localizar onde os dados específicos estão armazenados. 

Vantagens e Desvantagens:
- Vantagens: Maior capacidade de processamento (throughput), menor latência, e maior tolerância a falhas.
- Desvantagens: Aumenta a complexidade de gerenciamento, dificulta consultas complexas entre shards (cross-shard joins) e pode gerar desbalanceamento se a chave de distribuição for ruim. 

O sharding é comumente usado em bancos de dados NoSQL (como MongoDB) e em sistemas SQL de alta carga (como MySQL com partições) para suportar volumes massivos de dados e usuários

Vantagens de Desvantagens
- Divide dados em vários bancos para melhor performance e escalabilidade, distribuindo a carga entre servidores.
- Microgerenciamento de usuários via tabela
- Algoritimo que possibilita o "dividir para consquistar" e melhorar performance
- Melhora o Blast Radius, possibilitando a distribuição entre databases
- Possibilita Escalabilidade Horizontal para DBs
- Cuidado, algoritmo pode ter um limite que não possibilita o crescimento de novos usuários
- Alterar o algoritmo pode ser algo muito complexo e exigir o remanejamento de todos os dados
- Você precisa manter esse mapping que é controlado por você. Em consistente hash, o mapping é facilmente mantido e atualizado sempre que add/del targets

- "Blast radius" (raio de explosão) refere-se, no sentido físico, à área de destruição de uma explosão. No contexto de segurança da informação, é a extensão do impacto de um incidente, medindo sistemas e dados afetados por uma violação. Também refere-se à vulnerabilidade "Blast-RADIUS" no protocolo RADIUS.

*** Consistent Hashing ***

Consistent Hashing (Hashing Consistente) é uma técnica especial de hashing utilizada em sistemas distribuídos para distribuir dados entre vários nós (servidores) de forma eficiente. Diferente do hashing tradicional (ex: hash(chave) % n), ele minimiza a necessidade de remapear todos os dados quando servidores são adicionados ou removidos.
 
Por que usar?
Em um sistema de cache, se você tem 10 servidores e um cai, o hashing tradicional hash(chave) % 10 muda para hash(chave) % 9, o que faz quase todos os dados mudarem de servidor (falha de cache). O Consistent Hashing garante que, ao adicionar ou remover um servidor, apenas 1/n dos dados precisem ser movidos. 

Como funciona? (O Conceito do Anel)
1. Anel de Hash: Imagine um círculo (anel) onde os valores de hash vão de até um valor máximo grande (ex: 2^32-1).
2. Posicionamento de Servidores: Os servidores são mapeados no anel usando uma função hash baseada no seu IP ou nome.
3. Posicionamento de Dados (Chaves): Os dados (chaves) também são hashados e colocados no mesmo anel.
4. Localização: Para encontrar onde um dado está, mova-se no sentido horário a partir da posição da chave até encontrar o primeiro servidor. 

Exemplo Prático em Português
Vamos imaginar um sistema de cache com 3 servidores (A, B, C) e 5 itens de dados (D1, D2, D3, D4, D5).

1. Mapeamento no Anel
Imagine o anel como um relógio de 0 a 100.
- Servidor A: Hash = 10
- Servidor B: Hash = 40
- Servidor C: Hash = 70

2. Distribuição de Dados (Sentido Horário)
- D1 (Hash 5): Próximo servidor é A (10). -> Servidor A
- D2 (Hash 20): Próximo servidor é B (40). -> Servidor B
- D3 (Hash 50): Próximo servidor é C (70). -> Servidor C
- D4 (Hash 80): Passa pelo 70, volta ao início, próximo é A (10). -> Servidor A
- D5 (Hash 35): Próximo servidor é B (40). -> Servidor B

3. Adicionando um Novo Servidor (Servidor D - Hash 55)
O Servidor D entra entre B (40) e C (70).
- Antes: C era responsável por itens entre 40 e 70.
- Agora: D (55) assume a responsabilidade de C.
- Impacto: Apenas os dados que estavam entre o Servidor B e o novo Servidor D (como o D3, se estivesse no intervalo) mudam de servidor. Os dados de A e a maioria de B continuam onde estão. 

Vantagens
- Alta Escalabilidade: Adicionar/remover servidores afeta poucas chaves.
- Balanceamento de Carga: O uso de nós virtuais (onde um servidor físico é mapeado em vários pontos do anel) ajuda a evitar que um servidor receba muito mais carga que outros.
- Alta Disponibilidade: Essencial para sistemas como Cassandra, DynamoDB e caches distribuídos.

*** Shuffle Sharding ***

Para entender a diferença real, vamos imaginar um cenário com 12 servidores e 4 clientes (A, B, C e D). O objetivo é isolar os clientes para que, se um deles enviar uma "query da morte" (que trava o servidor), os outros continuem online.

1. Exemplo de Sharding Tradicional (Baseado em Grupos)
No sharding tradicional, você divide sua infraestrutura em "ilhas" fixas.
- Configuração: 12 servidores divididos em 3 shards (grupos) de 4 servidores cada.
- Distribuição:
-- Shard 1 (Servidores 1, 2, 3, 4): Atende o Cliente A.
-- Shard 2 (Servidores 5, 6, 7, 8): Atende o Cliente B.
-- Shard 3 (Servidores 9, 10, 11, 12): Atende os Clientes C e D.

O cenário de falha:
Se o Cliente C enviar uma requisição que consome 100% da CPU ou trava o banco de dados em todos os servidores onde ele está, os servidores 9, 10, 11 e 12 cairão.
- Resultado: O Cliente D fica 100% fora do ar, mesmo não tendo feito nada de errado. Eles estão no mesmo "barco".
- Raio de impacto: 25% dos clientes (1 em 4) foram afetados injustamente.

2. Exemplo de Shuffle Sharding (Baseado em Combinações)
Aqui, não existem grupos fixos. Cada cliente recebe uma combinação virtual única de servidores. Vamos supor que cada cliente use 2 servidores (shards virtuais).
- Configuração: 12 servidores disponíveis.
- Distribuição (Exemplo de combinações aleatórias):
-- Cliente A: Servidores [1, 5]
-- Cliente B: Servidores [2, 8]
-- Cliente C: Servidores [3, 10]
-- Cliente D: Servidores [4, 10]

O cenário de falha:
Se o Cliente C enviar a mesma "query da morte", ele derrubará os servidores 3 e 10. Vamos ver o que acontece com os outros:
- Cliente A: Zero impacto (usa 1 e 5).
- Cliente B: Zero impacto (usa 2 e 8).
- Cliente D: Impacto Parcial. O servidor 10 caiu, mas ele ainda tem o servidor 4 funcionando perfeitamente. O sistema fica mais lento para ele, mas não sai do ar.

Por que é mais poderoso?
Com 12 servidores escolhendo 2 para cada cliente, existem 66 combinações possíveis.
- No Sharding Tradicional, se você tem 4 grupos, a chance de dois clientes compartilharem o mesmo destino é de 25%.
- No Shuffle Sharding, a chance de o Cliente D compartilhar exatamente os mesmos dois servidores que o Cliente C (e cair totalmente junto com ele) é de apenas 1 em 66 (1,5%).

Resumo da diferença
Característica	Sharding Tradicional		Shuffle Sharding
Estrutura	Grupos rígidos e isolados.	Combinações sobrepostas.
Falha de um nó	Derruba todos no grupo.		Afeta apenas quem compartilha aquele nó específico.
Raio de Impacto	Grande (todo o shard).		Mínimo (apenas a combinação exata).
Complexidade	Simples de implementar.		Requer um roteador/load balancer inteligente.

*** Shuffle Sharding com Consistent Hashing ***

Sim, é possível e comum usar Shuffle Sharding com Consistent Hashing em sistemas distribuídos de alta escala [5.2]. Essa combinação é poderosa porque une a alta disponibilidade e isolamento de falhas do Shuffle Sharding com a distribuição uniforme e escalabilidade do Consistent Hashing. 

Aqui está como os dois conceitos funcionam juntos:
1. Como Funciona a Combinação
Consistent Hashing (Distribuição): O hashing consistente mapeia servidores e chaves de dados (ou usuários) em um anel lógico. Isso garante que, se um servidor falhar, apenas uma fração dos dados precise ser remapeada.
2. Shuffle Sharding (Isolamento): Em vez de atribuir um usuário a um único "shard" (servidor), o shuffle sharding atribui a cada usuário um subconjunto de "shards" (ex: 2 de 10). 

Integração:

- Utiliza-se o hashing consistente para determinar o "anel" de servidores disponíveis.
- A partir desse anel, o Shuffle Sharding seleciona, de maneira determinística, um subconjunto de nós para cada inquilino (tenant).
- Isso significa que o inquilino A e o inquilino B podem compartilhar alguns servidores, mas é muito improvável que compartilhem todos os mesmos servidores, isolando falhas. 

Vantagens dessa Combinação
- Isolamento de Falhas (Shuffle Sharding): Se um servidor cair, apenas os tenants que usam aquele subconjunto específico de servidores são afetados, evitando o efeito "efeito dominó" em todo o sistema 
- Escalabilidade e Eficiência (Consistent Hashing): Adicionar ou remover nós do anel afeta minimamente a distribuição existente, mantendo a carga balanceada.
- Zone-awareness: É possível garantir que o subconjunto de instâncias selecionadas para um inquilino esteja distribuído entre diferentes zonas de disponibilidade (Availability Zones).

Exemplo prático: O sistema CortexMetrics usa essa abordagem para gerenciar métricas de alto volume, garantindo que o impacto de um inquilino ruidoso ou uma falha de servidor seja limitado ao menor número possível de outros inquilinos.

*** Cache Aside Pattern ***

- Carrega dados no cache sob demanda: se ausentes, busca no banco, coloca no cache e retorna
- Lazy-loading. Eficiente somente para dados realmente consultados
- Melhora tempo de resposta consideravelmente
- Resiliente em caso de falhas, pois ele vai para o DB
- importante analisar se você realmente precisa de um in-memory db
- Cuidado, cache-miss pode gerar mais latência se não paralelizar ou fazer update do cache em background
- Aplicação precisa implementar o padrão via código
- Gerenciar a Expiração / Consistência Eventual
